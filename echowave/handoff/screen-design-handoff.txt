The direction
Build one assistant that feels simple at the front and accountable behind the scenes. Keep Chat and Today as the two primary destinations. Put the five helpers, meetings, learning, saved work and advanced workflows within that structure. Give staff a separate operating console with useful evidence and controlled actions.
This design companion adds concrete layouts and interaction rules to the Product and Engineering Handoff. The original handoff remains the source for architecture, permissions, operational limits and capability gates. The layouts here are implementation targets; they do not certify that a feature is live.
How to use this document
Read the reference decisions and shared rules first. Then implement each numbered screen sheet with its loading, error, permission and mobile states. Use the final Claude instruction with both documents. Map logical destinations onto existing routes before changing any URL.

Interaction rules
Every detail view has a stable deep link and browser Back behavior. Overlay Escape closes only when no protected work would be lost, then restores focus to the trigger. Trap focus only inside a real modal; a nonmodal desktop side panel stays in normal reading order.
At 200 percent zoom, prioritize reflow over keeping columns. Keep the main document free of horizontal scrolling; a true data table or canvas can have its own labelled scroll region and an accessible alternative. Long names, addresses and Tamil/Hindi text wrap.
For streaming, announce status changes politely, not every token. Preserve user scroll position. When switching personal/workspace scope, clear prior records before rendering the next scope; reauthorize subscriptions and queries.
Test 360, 390, 768, 1024 and 1440 px widths; 200 percent zoom; keyboard-only input; screen reader labels; iPhone software keyboard; reduced motion; slow network; and long localized labels. Native app release remains separately verified.

Shared state and data contracts
Contract
UI requirement
Task state
Queued, running, needs input, awaiting approval, scheduled, completed, failed, cancelled and outcome unknown. Completion requires persisted or reconciled evidence.
Freshness
Use loading, empty, stale, partial and failed as distinct states. Display last successful refresh and coverage. Preserve stale values with a label after a failed refresh.
Save state
Dirty → saving → confirmed saved. On rejection retain draft plus last confirmed value. Revision conflict shows both versions; never silently overwrite.
Capability state
Available, needs setup, disabled by policy or unavailable with reason and next step. Frontend visibility never replaces backend authorization.
Approval state
Preview ID/version, exact payload, account, recipient, attachments, timing, expiry and consequence. Editing invalidates approval; execution is idempotent.
Scope
Every task, record, connection, preference and subscription belongs to personal or workspace scope. Permission checks precede retrieval and execution.
Event delivery
State version and sequence reject stale updates. On reconnect fetch authoritative state, then resume events. Preserve drafts; polling fallback uses backoff.
Operational action
Typed command, role, environment, target, reason, approval, idempotency key and result. Accepted is queued, not succeeded.
Privacy
No prompts, transcripts, audio, secrets, KYC documents or raw email in analytics. Replay off on sensitive screens. Redacted error codes replace raw payloads.
Reusable error copy
No records: “Nothing due in Decibyl.” Partial brief: “Calendar could not refresh. This brief includes mail only.” Save failure: “Your change was not saved. Try again.” Unknown send: “We are checking whether this was delivered. Please do not send it again.”
Errors should identify the failed step and a safe next action. Keep staff diagnostics behind permitted details. Success toasts acknowledge confirmed state and never replace durable status on the record.

Metrics events and release proof
Metric
Definition displayed in the console
Activation
First meaningful successful outcome after onboarding, according to the helper contract. A first message is not sufficient.
Weekly useful users
Distinct users with at least one defined useful outcome in the selected seven-day window.
Seven day repeat
Activated users with a further useful outcome in days 1–7 after activation divided by users whose full window elapsed. Label this exact window.
Task success
Successful eligible attempts / eligible attempts. Show partial, unknown, cancelled and excluded counts and the cancellation policy.
Usefulness
Positive responses / answered feedback prompts; show exposure count and response rate separately.
Cost per success
All attributable attempt costs, including failed attempts, divided by successful outcomes in the same cohort/period. Label estimates.
Voice latency
Speech end to first meaningful audible response at client, p50/p95 and sample size by language/channel/provider. Report interruption separately.
Support and finance
First response, resolution, reopen rate and CSAT with sample sizes. Separate cash, refunds, recurring value, recognized revenue and service costs.

Reconcile names with repository constants before adding events.
Server events own business outcomes. Client events describe intent only. Envelope: event_id, schema_version, occurred_at UTC, environment, release, pseudonymous user_id, workspace_id/task_id when applicable, trace_id and configuration_version. Use typed channel/language/status/reason/duration properties. Dedupe important delivery; analytics must not block voice or alter the ledger.

Suggestions and Claude execution brief
Six focused product improvements
Make task evidence the signature detail A compact receipt under each completed action should show what happened, where, when and how to verify it. Reuse S09 across every channel.
Make source coverage visible A small “2 of 3 sources checked” disclosure on briefs builds more trust than an impressive-looking answer that hides a failed connection.
Teach in context Offer one dismissible tip after a relevant success, such as scheduling a brief after planning today. Keep a Help route to replay guidance; no compulsory feature tour.
Build the founder attention queue first Put unresolved failures, waiting approvals, support escalations and spend exceptions at the top of S29. This makes daily operation actionable.
Connect support to quality Turn a permitted sanitized failure into an evaluation case, then link the fix and release. This creates a visible improvement loop.
Keep advanced capability discoverable Use searchable Settings, helper details and deep links to preserve skills, workflows and provider controls without expanding primary navigation.
