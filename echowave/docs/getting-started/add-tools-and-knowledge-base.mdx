---
title: "Use External Tools, Knowledge"
description: "Let the agent check a live system mid-call, and answer policy questions from your own documents."
---

An agent that can only talk is a script with a nicer voice. This page connects
it to two things it does not know: your live systems, and your written policies.

Which one you need depends on whether the answer changes:

| | Use a **tool** | Use the **Knowledge Base** |
| --- | --- | --- |
| The answer | Changes per caller, per minute | Is the same every time |
| Examples | Order status, slot availability, account balance | Return policy, shipping FAQ, price list |
| Mechanism | An HTTP request the agent makes mid-call | Text retrieved from a document you uploaded |

The example on this page is **Maya**, an order-support agent for a store called
**QuickMart**. She can check what is in a caller's cart (a tool) and answer
questions about returns (a document).

<Steps>

<Step title="Create the tool">

Open the node where the conversation happens — Maya's main support node — scroll
to **Tools**, and click **Create a Tool → External HTTP API**. Name it
`get_cart_details`.

<Screenshot
  src="tools-create-http-tool.png"
  alt="The tool creation form with name, description, HTTP method and endpoint URL"
  caption="The description is the only field the model reads. Write it for the model, not for yourself."
  shot="The Create Tool / HTTP API form filled in for get_cart_details: name, a full sentence description, GET method, and the dummyjson endpoint. Decibyl branding, dark theme."
/>

<Note>
**The description does all the work.** It is the only thing the model sees when
deciding whether to call this tool. Write a sentence that says when to use it
and what comes back:

> *Use this tool when the caller asks about cart details. It returns the cart's
> products, quantities, total, and discounted total.*

A description like "gets cart" leaves the model guessing, and a model guessing
about tools either calls the wrong one or calls none.
</Note>

For the endpoint, this example uses a public sample API so you can try it with
no backend of your own:

```http
GET https://dummyjson.com/carts/1
```

No authentication, no parameters. It is a `GET` because it reads rather than
changes anything. In your own build this would point at your order system.

Save the tool.

</Step>

<Step title="Attach the tool to the node">

Creating a tool does not give it to anybody. Go back to Maya's node, find
**Tools**, and select `get_cart_details`. Save.

<Screenshot
  src="tools-attach-to-node.png"
  alt="An Agent node's Tools selector with get_cart_details selected"
  caption="A tool is available on the nodes you attach it to, and nowhere else."
  shot="An Agent node settings panel scrolled to the Tools section, with get_cart_details selected in the picker."
/>

<Warning>
This is the step people skip. An unattached tool exists in your workspace, shows
up in the tools list, and will never be called — because the agent is only told
about tools attached to the node it is currently on. Attaching per node is
deliberate: it stops a checkout tool being reachable during the greeting.
</Warning>

</Step>

<Step title="Upload a Knowledge Base document">

Click **Upload Document**, or go to **Knowledge Base Files**. Pick something
your customers actually ask about — a returns policy, a shipping FAQ.

Decibyl asks how the agent should read it:

- **Full Document** — the agent sees the whole file. Best for anything short.
  Needs no embedding model.
- **Chunked Search** — the agent retrieves only the relevant section. For long
  documents. **Configure an embedding model first**, under Model Configurations;
  without one, processing or retrieval fails.

A two-page policy is a Full Document case. Upload it and wait for the status to
read **Completed** before going further.

<Screenshot
  src="knowledge-base-upload.png"
  alt="The Knowledge Base file list showing an uploaded document with Completed status"
  caption="Wait for Completed. A document still processing is not yet retrievable."
  shot="The Knowledge Base Files list with one document (e.g. 'QuickMart returns policy.pdf') showing retrieval mode Full Document and status Completed."
/>

</Step>

<Step title="Attach the document to the node">

Same rule as the tool. Back on Maya's node, scroll to **Knowledge Base
Documents**, and attach the file.

Uploading makes the document available to your workspace. Attaching makes it
available to the conversation.

</Step>

<Step title="Tell the agent which is which">

The model does not infer your architecture. Say it in the node's prompt:

```text title="Added to Maya's prompt"
If the caller asks about cart contents, order items, quantities, total, or
discounts, use the get_cart_details tool before answering. Never guess at
cart contents.

For questions about returns, refunds, or cancellations, answer from the
attached Knowledge Base document.
```

Save the node.

</Step>

<Step title="Test both paths">

Start a **Test Agent → Test Audio** call and try one of each:

- *"Hi Maya, what's in my cart?"* — watch the transcript. She decides the tool
  applies, calls the API, and answers from the response.
- *"What's your return policy?"* — she answers from the document instead.

<Screenshot
  src="tools-test-call-tool-invocation.png"
  alt="A test call transcript showing the get_cart_details tool being called with its arguments and response"
  caption="Tool calls appear inline in the transcript, with arguments and response."
  shot="A live test transcript showing a tool call entry for get_cart_details expanded to show arguments and the JSON response, followed by the agent's spoken answer."
/>

If she answers a cart question without calling the tool, the description is the
thing to fix — not the prompt.

</Step>

</Steps>
