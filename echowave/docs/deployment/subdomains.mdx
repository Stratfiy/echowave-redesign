---
title: "Splitting onto subdomains"
description: "Serving the app, the API and the docs from their own hostnames, with the apex free for a marketing site."
---

The default deployment serves everything from one hostname and splits by path:
`/api/v1/` to the API, `/` to the app. That is correct for a self-hosted
install and you should leave it alone.

This page is for the commercial deployment, where you want:

| Hostname | Serves |
|---|---|
| `decibyl.ai` | marketing site — **not** served by this stack |
| `app.decibyl.ai` | the product |
| `api.decibyl.ai` | API, WebSockets, MCP server, embed widget |
| `docs.decibyl.ai` | documentation |

<Warning>
**The split makes the browser cross-origin.** That is the one thing capable of
breaking it. It is safe today because the app authenticates with a **Bearer
token, not a cookie** — there is no SameSite problem to solve. If auth ever
moves to cookies they must be issued on `.decibyl.ai` with `SameSite=None`, and
`CORS_ALLOWED_ORIGINS` must stop being a wildcard: browsers reject a wildcard
origin on a credentialed request.
</Warning>

## 1. DNS

Four records.

| Type | Name | Value |
|---|---|---|
| A | `app` | your Elastic IP |
| A | `api` | your Elastic IP |
| A | `docs` | your Elastic IP |
| A / CNAME | `@` | your Elastic IP, **or** your marketing host once one exists |

The apex has two supported answers and you can change your mind later without
touching nginx:

- **Point it here.** It is served empty — a 404 with a pointer to the app —
  until you drop a built site into `/usr/share/nginx/landing`. This is the
  right choice while the marketing site does not exist yet, because the name
  still resolves and still gets a certificate.
- **Point it at a site host** (Vercel, Webflow, S3). The apex block then never
  sees a request.

What the apex must **not** do is redirect to `app.`. It works today and is in
the way the moment there is a landing page to put there.

Wait for the records to resolve before going further. Certificate issuance
fails against a name that does not resolve, and the failure message points at
the wrong thing:

```bash
dig +short decibyl.ai app.decibyl.ai api.decibyl.ai docs.decibyl.ai
```

## 2. Certificates

One certificate covering every name this box answers on. Miss one and that
hostname fails with a certificate error before nginx gets to route it, which
looks nothing like a routing problem and sends you looking in the wrong place.

```bash
sudo certbot certonly --webroot -w ./certs \
  -d decibyl.ai -d www.decibyl.ai \
  -d app.decibyl.ai -d api.decibyl.ai -d docs.decibyl.ai \
  --email you@decibyl.ai --agree-tos --no-eff-email

# nginx reads these paths; point them at the issued certificate
sudo ln -sf /etc/letsencrypt/live/app.decibyl.ai/fullchain.pem ./certs/local.crt
sudo ln -sf /etc/letsencrypt/live/app.decibyl.ai/privkey.pem   ./certs/local.key
```

Drop `-d decibyl.ai -d www.decibyl.ai` if the apex points at a marketing host
rather than at this box, and drop `-d docs.decibyl.ai` if the docs are hosted
elsewhere. Everything else is required.

## 3. Configuration

In `.env` on the box:

```bash
# The API's own public URL. Telephony providers call webhooks here, the SDK
# targets it, and the MCP server is advertised at it — so this is the one
# hostname that must not move once customers have integrated.
BACKEND_API_ENDPOINT=https://api.decibyl.ai
PUBLIC_BASE_URL=https://api.decibyl.ai

# What the browser bundle calls. Baked in at build time, so the UI image must
# be rebuilt after changing it — not just restarted.
NEXT_PUBLIC_BACKEND_URL=https://api.decibyl.ai

# Recordings are fetched from the API host.
MINIO_PUBLIC_ENDPOINT=https://api.decibyl.ai

# Only needed when DEPLOYMENT_MODE is not "oss". In oss mode the API already
# allows any origin without credentials, which is correct for Bearer auth.
CORS_ALLOWED_ORIGINS=https://app.decibyl.ai
```

<Warning>
`NEXT_PUBLIC_*` variables are compiled into the browser bundle. Changing one
and restarting does nothing — the old value is inside the built JavaScript.
Rebuild the UI image.
</Warning>

## 4. Build the docs

The docs subdomain serves static HTML off disk. Nothing builds it for you, and
an unbuilt `docs/dist/` means `docs.decibyl.ai` answers 404 — so do this before
rendering nginx, not after.

```bash
cd docs
npm ci
npm run build          # -> docs/dist
npm run check-links    # fails the deploy on a broken internal link
cd ..
```

Skip this only if you are not serving docs from this box.

## 5. Name the hosts

Add these to `.env`. Setting `DECIBYL_APP_HOST` is what switches the
deployment from one hostname to four — `decibyl-init` renders the subdomain
config on the next `docker compose up`, so there is no separate command to
remember and no way to deploy having forgotten it.

```bash
DECIBYL_ROOT_HOST=decibyl.ai        # optional; derived from the app host
DECIBYL_APP_HOST=app.decibyl.ai
DECIBYL_API_HOST=api.decibyl.ai
DECIBYL_DOCS_HOST=docs.decibyl.ai
```

```bash
docker compose build ui        # picks up NEXT_PUBLIC_BACKEND_URL
docker compose up -d
docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload
```

Leave `DECIBYL_APP_HOST` unset and you keep the single-host config, which is
still the right choice for a self-hosted install on one name.

### What each hostname answers

| Host | Serves |
|---|---|
| `decibyl.ai` | **Nothing.** 404 with a pointer to the app, until you put a landing site in `/usr/share/nginx/landing` or move the apex to a site host in DNS |
| `app.decibyl.ai` | The product |
| `api.decibyl.ai` | API, WebSockets, MCP, the embed widget |
| `docs.decibyl.ai` | Static documentation |
| anything else | Connection closed (444) |

That last row matters more than it looks. nginx serves the *first* block on a
port to any hostname it does not recognise, so without an explicit catch-all
the app answers for every name anyone points at your IP.

<Warning>
Until this is rendered, **every hostname resolves to the same default server
block** — whichever one nginx loads first. The symptom is subtle: `docs.` and
`api.` both serve the dashboard, so the docs host redirects to a login page and
looks like an auth bug rather than a routing one. `nginx -T | grep server_name`
tells you what is actually loaded.
</Warning>

## 6. Check it, in this order

Each step tells you something the previous one could not.

```bash
# 1. The API answers on its own hostname
curl -s https://api.decibyl.ai/api/v1/health | jq .status

# 2. The app is served, and is NOT reachable on the API host
curl -sI https://app.decibyl.ai | head -1
curl -s https://api.decibyl.ai/ | jq -r .detail     # expect the pointer message

# 3. Cross-origin actually works from the browser's point of view
curl -si -X OPTIONS https://api.decibyl.ai/api/v1/health \
  -H "Origin: https://app.decibyl.ai" \
  -H "Access-Control-Request-Method: GET" | grep -i access-control

# 4. WebSockets upgrade — this is what carries voice
curl -si https://api.decibyl.ai/api/v1/health \
  -H "Connection: Upgrade" -H "Upgrade: websocket" | head -1

# 5. Docs are served, and a missing page is a real 404 rather than the
#    dashboard's login redirect
curl -sI https://docs.decibyl.ai/getting-started | head -1
curl -so /dev/null -w "%{http_code}\n" https://docs.decibyl.ai/not-a-page

# 6. The apex is empty, and does NOT serve the app
curl -s https://decibyl.ai/ | jq -r .detail
```

<Note>
A `307` to `/auth/login` from any of these means nginx never matched a
`server_name` and fell through to the app. Re-run step 5.
</Note>

Then log in at `https://app.decibyl.ai` and place one test call. Nothing above
proves audio works; only a call does.

## 7. Repoint the things that hold your old URL

Splitting hostnames silently invalidates anything that stored the old one:

- **Telephony webhooks.** Every provider's callback URL must become
  `https://api.decibyl.ai/...`. An inbound call to a stale URL fails with no
  error on your side — the carrier gets the 404, you get silence.
- **The Razorpay webhook**, to
  `https://api.decibyl.ai/api/v1/billing/razorpay/webhook`. Miss this and
  payments are captured and never credited, which is the failure the billing
  readiness check exists to catch.
- **Embed widget snippets** already on customer sites, which point at the old
  host. Regenerate and reissue them.
- **`SENTRY_ORG` / source maps**, if the app URL changed.

<Note>
**`/api/` deliberately keeps working on `app.decibyl.ai`.** `api.decibyl.ai` is
canonical and is what new integrations should use, but the MCP endpoint is
published as `https://app.decibyl.ai/api/v1/mcp/` in
[MCP Server](/integrations/mcp) and the API reference — and every customer who
has already run `claude mcp add` has that URL saved in their own config.
Serving only the UI there would break all of them silently: their assistant
would simply stop finding the tools.

Published integration URLs are a contract. Migrate them with a deprecation and
notice, not as a side effect of splitting hostnames.
</Note>

<Note>
Serving the OpenAPI schema publicly at `api.decibyl.ai` is normal and fine, but
check the Razorpay webhook is still `include_in_schema=False`. It is excluded
deliberately — it carries no session, and the HMAC signature is its
authentication.
</Note>

## Why the apex is not proxied here

Redirecting `decibyl.ai` to `app.decibyl.ai` would work today and be in the way
the moment a marketing site exists. Point the apex at your site host in DNS and
keep this stack out of it — the two have different uptime requirements, and a
marketing page that goes down with the API is a marketing page that cannot tell
anyone the API is down.
