---
title: "Rotating secrets"
description: "Every secret the stack holds, where it lives, and how to rotate it without downtime"
---

This runbook exists so that a leaked key is a ten-minute job, not an
investigation. It lists every secret the API, worker and UI read, where the
live value is kept, what breaks while it is wrong, and the order of steps.

Rotate first, investigate second. A key that was pasted into a chat, a ticket
or a screenshot is compromised the moment it left the terminal.

## Where the values live

| Deployment | Where | How it reaches the containers |
| --- | --- | --- |
| Production (EC2, docker-compose) | `.env` beside `docker-compose.yaml` on the box, owned by the deploy user | `scripts/ci_deploy.sh` runs `docker compose up -d`; a changed `.env` needs a `docker compose up -d <service>` to take effect |
| Self-hosted (Docker guide) | `.env` written by `setup_remote.sh` | same |
| Local development | `.env` in `echowave/` | `docker compose` / `uvicorn` reads it at start |

Nothing reads a secret at request time from the environment file; every
secret is read once at process start (`api/constants.py`). So a rotation is
always: change the value at the source, change `.env`, restart the affected
service, confirm, revoke the old value.

## Order of steps

1. **Create the new value** at the source (vendor console, `openssl rand -hex 32`, Fernet generator). Do not revoke the old one yet.
2. **Write it to `.env` on the box** with an editor over SSM or SSH. Never paste it into a chat, a Jira issue or a commit.
3. **Restart only the services in the table**: `docker compose up -d api worker`. Both read the file at start.
4. **Confirm**: `GET /api/v1/health` is green; for a carrier or payment key, place one test call or one ₹1 top-up; for Redis, check that the worker heartbeat row advances (`api/tasks/heartbeat.py`).
5. **Revoke the old value** at the source.
6. **Record** the rotation (date, secret name, who) on the security issue. Not the value.

## Fernet key (`PLATFORM_CREDENTIAL_SECRET`)

The stored provider keys and carrier credentials are encrypted with this key,
and the cipher is a single `Fernet`, not a `MultiFernet`. Changing the value
without re-encrypting makes every stored credential unreadable:
`organization_credentials.py` raises on decrypt and the bots show "key
rejected" cards.

Until a re-encryption command exists, rotation is a maintenance step:

1. Export the plaintext credentials with the old key (a one-off script run
   on the box, output kept only in memory or a file that is shredded after).
2. Set the new key, restart api and worker.
3. Re-enter each credential through the app (Staff → Platform credentials;
   customers re-enter their own keys) or re-encrypt with the script.
4. Shred the export.

A `MultiFernet` with `PLATFORM_CREDENTIAL_SECRET_PREVIOUS` for zero-downtime
rotation is the right fix and is tracked on the security issue; do not
improvise it during an incident.

## Razorpay webhook secret

Credit is applied only by the webhook (`routes/payments.py`), never
by the browser. While the secret is wrong every payment is taken from the
customer and **not credited**. Rotate it at a quiet hour, restart the api
first, then switch the value in the Razorpay dashboard, so the window in which
the two disagree is seconds. Reconcile any payment in that window from the
Razorpay dashboard against the credit ledger.

## Keys pasted in the past

Two keys were pasted into build chats in September 2026 (a SerpApi key and a
workspace `dcb_` key) and are tracked for rotation on KAN-233. Treat any key
that appears in a transcript the same way: rotate, then delete the message.
